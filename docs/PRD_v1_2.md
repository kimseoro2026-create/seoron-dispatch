## 1. 제품 정의

퇴원 고령자의 병원동행·가사지원 요청과 돌봄 인력의 가용 시간·자격·동선을 함께 고려해, 같은 인력과 예산으로 필요한 시점에 지원받는 사람을 늘리는 담당자 승인형 운영지원 시스템.

사업 목표는 물리적 돌봄 제공의 확대다. 요청 구조화와 기록은 배정에 필요한 입력을 준비하는 수단이다. 새로운 상담일지 작성이나 메모량 증가를 성과로 삼지 않는다.

### 핵심 사용 흐름

기존 자료 가져오기 → 필수 조건 검토 → 인력·근무·협약 확인 → 배정안 계산 → 담당자 승인·인력 수락 → 현장 일정 → 취소·지연 재배정 → 효과 비교·부족 자원 분석.

### 제품이 답할 질문

1. 오늘 필요한 요청 중 누가 어떤 시간에 수행할 수 있는가?
2. 기존 서비스 시간을 줄이지 않고 추가로 지원할 수 있는 요청은 무엇인가?
3. 취소·지연이 생겼을 때 진행 중 돌봄을 보호하면서 어떻게 일정을 바꿀 것인가?
4. 해결되지 않은 원인이 정보 부족인지, 자격·시간·지역·예산 부족인지 구분할 수 있는가?
5. 인력이나 협약기관을 추가하면 적기 지원이 얼마나 늘어나는가?

M1~M3는 개발 순서이며 사업 목표 축소가 아니다. 제안서의 공동 동행·예측·정책 근거 기능을 M3 실험에 포함하되, 실제 운영 가능성과 예측 정확도를 가상 데이터로 입증했다고 표현하지 않는다.

### 최초 구현의 기본값

- 서비스: `hospital_escort`, `household_support`.
- 한 기관·한 가상 권역을 기본으로 하되 협약기관 데이터를 추가할 수 있게 설계.
- 1:1 지원 기본. 공동 동행·구간 분리는 실험 모드에서만 사용.
- 화면·업무시간: Asia/Seoul. 저장은 UTC 시각과 기관 timezone을 사용. 날짜만 있는 퇴원일은 date로 보존.
- 합성 데이터만 사용. 사람·병원·기관의 샘플은 명시적으로 가상 표시. 공개 병원 위치를 사용할 경우 시설정보의 실제 출처와 합성 이용자를 구별.
- 외부 서비스 키가 없으면 명시적인 mock adapter 사용. “연결 완료”와 “가상 응답”을 분리.
- 모델·라이브러리 버전은 개발 첫날 실행환경에서 검증 후 lockfile에 고정. 이 문서는 특정 최신 버전을 가정하지 않음.

### 최초 출시에서 하지 않는 일

의료적 필요·복지 자격 자동 판정, 자동 예약 변경, 자동 현장 파견, 실제 개인정보 기반 학습, 인력 GPS 상시 추적, 취소 예측만으로 예약 취소·초과 예약, 전국 운영망 구축, 공공기관 도입 인증 완료 주장.

## 3. 사용자와 권한

| 역할 | 조회 | 생성·변경 | 제한 |
|---|---|---|---|
| 기관 관리자 | 본인 기관·공유 허용 정보 | 계정, 근무규칙, 비용, 협약, 연결 설정 | 타 기관 원문 조회 불가 |
| 배정 담당자 | 담당 기관 요청·인력·배정 | 입력 검토, 계획 실행, 승인·반려, 재배정 | 이용 자격·의료 판단 자동화 금지 |
| 현장 인력 | 본인 확정·제안 일정의 필요한 정보 | 수락·거절, 이동·시작·완료·지연 상태 | 다른 인력·기관 전체 요청 조회 불가 |
| 평가 담당자 | 가상 실험 입력·지표·집계 결과 | 실험 실행·내보내기 | 실운영 배정 승인 권한 없음 |

MVP는 가상 계정으로 역할별 테스트한다. Supabase를 적용하는 공유 배포에서는 UI 숨김뿐 아니라 DB RLS와 서버 권한검사를 모두 적용한다. 기관 간 공유는 협약의 서비스·권역·유효기간·공유필드 범위 안에서만 가능하다.

## 4. 핵심 지표와 성공 조건

### 4.1 지표 정의

| 지표 | 계산·해석 |
|---|---|
| 적기 배정 요청 수 | 검증 통과한 배정 중 필수 시작 마감·예약 도착·완료 시간 조건을 모두 충족하는 요청 수 |
| 적기 지원 가능 고유 인원 | 적기 배정 요청이 1건 이상인 beneficiary_id의 중복 제거 수. 전체 필요 서비스 충족과 구분 |
| 필수 요청 전체 충족 인원 | 기간 내 해당 대상자의 모든 필수 요청이 적기에 배정된 고유 인원 |
| 실제 적기 완료 인원 | 현장 실증의 완료시각으로 집계. 시뮬레이션에서는 “가상 수행 결과”로 별도 표기 |
| 미배정 요청 수 | 유효 요청 중 배정되지 않은 수. 자료 불충분 요청은 별도 집계 |
| 이동시간 | 근무 중 요청 간 이동 + 동행 내부 이동. 중복 합산 금지. 출퇴근 포함 여부 명시 |
| 담당자 업무시간 | 가져오기·오류 수정·검토·승인·재배정에 실제 소요된 시간. 사용성 평가에서 측정 |
| 비용 | 인건비·교통비·운영비·시스템비 합계. 고정급/시간급 모델 구분 |
| 서비스 품질 보호 | 필수시간 축소·자격 위반·이중 배정·휴게 위반 건수, 고우선순위 미충족 수, 변경 횟수 |

### 4.2 출시 기준과 사업 가설의 분리

출시 필수: 하드 제약 위반 0건, 승인 경합 테스트 통과(M2부터, 다기관 권한은 후속), 동일 입력으로 재현 가능한 비교, 오류·미배정 사유 노출, 수치 출처 추적 가능.

사업 검증: 기존 기준선 대비 지원 증가·이동 감소·순비용 변화는 측정 결과로 보고한다. 개선이 없는 조건과 악화 조건도 보고한다. 제출본의 31% 절감·1.45배 지원은 검증 가설이며 UI 상수·성공 기준·기본 결과값으로 사용하지 않는다.

## 5. 화면별 기능 요구사항

우선순위 P0는 M1 필수, P1은 M2~M3 필수, EXP는 실험 전용이다. 아래 모든 요구사항은 빈 데이터·처리중·실패·권한 없음 상태를 제공한다.

### W01 오늘의 돌봄 현황

- FR-01 [P0] 날짜·기관·서비스·담당자 우선순위로 요청과 배정을 필터링한다.
- FR-02 [P0] 유효 요청, 자료 확인 필요, 제안, 승인 대기, 확정, 진행, 완료, 미배정을 서로 다른 상태로 집계한다.
- FR-03 [P0] 첫 지원 마감 임박·취소·지연을 우선 표시하되 담당자 우선순위 설정을 보여준다.
- FR-04 [P0] 집계 시각, 자료 동기화 상태, 가상/공개/기관 데이터 모드를 표시한다.
- 검수: 필터된 표와 카드 집계가 일치하며, 배정 2건의 동일 대상자를 고유 인원 2명으로 계산하지 않는다.

### W02 자료 불러오기

- FR-05 [P0] CSV, 텍스트 붙여넣기, 샘플 로드 제공. 외부 열 이름을 내부 필드에 매핑하고 미리보기를 제공한다.
- FR-06 [P1] XLSX·텍스트 PDF·동의받은 모의 음성 지원. 스캔 PDF는 OCR 도입 전 지원 불가 안내.
- FR-07 [P0] 문서 파일 10MB, 오디오 20MB·10분을 초기 앱 제한으로 설정한다. 공급자 제한이 더 낮으면 낮은 값 적용. 파일 내용·확장자 검사.
- FR-08 [P0] 파일 해시로 중복 업로드를 알리고, 기관+외부 요청 ID로 행 중복을 검토한다. 기존 요청 덮어쓰기는 담당자가 변경사항을 확인한 경우에만 허용.
- FR-09 [P0] 성공·오류 행 수와 오류 위치를 표시한다. 정상 행도 draft로 생성하며 검토 전 배정하지 않는다.
- FR-10 [P1] 처리 job은 queued/running/succeeded/partial/failed 상태, 재시도·원문 삭제를 제공한다.
- 검수: 잘못된 날짜 한 행 때문에 전체 자료를 잃지 않으며 재업로드가 요청 중복을 만들지 않는다.

### W03 요청 카드 검토

- FR-11 [P0] 원문과 필드값·근거 구간을 나란히 표시한다. 추출값, 담당자 수정값, 수정자를 보존한다.
- FR-12 [P0] 서비스 종류, 대상자 ID, 시간창, 위치, 필수시간, 필요한 자격·지원조건을 검증한다.
- FR-13 [P0] 퇴원예정일/실제 퇴원일, 상담일/서비스일, 외래 예약/첫 지원 마감을 별개로 저장한다.
- FR-14 [P0] 미확정 주소·지원시간·자격조건은 needs_review로 두며 임의 기본값으로 확정하지 않는다.
- FR-15 [P0] 확인 완료, 보류, 수정, 취소를 제공. 주소 좌표 후보가 여러 개인 경우 선택을 요구한다.
- 검수: “보행기 사용”을 “자립보행 가능”으로 자동 변환하지 않는다. 연도 없는 날짜는 자동 확정하지 않는다.
- FR-57 [P0] 배정 계산에 필요한 필드(서비스 종류, 서비스일, 시간창, 위치, 필수시간, 필요 자격)만 승인 차단 사유로 쓴다. 나머지 확인 필요 항목은 목록에서 일괄 확인할 수 있게 하고, 사용성 평가에서 요청 1건당 검토 조작 수를 기록한다.

## 6. 배정 엔진 요구사항

### 6.1 입력·출력

입력: 검토 완료 요청, 날짜별 인력·자격·근무, 고정 일정, 방향별 이동시간, 기관 협약, 우선순위, 서비스시간, 비용·예산 가정, 실행시점.

출력: 요청-인력 배정, 전체 시간구간, 적기 여부, 제약 검증결과, 미배정 사유·진단 수준, 실행지표, 변경 영향, 솔버 종료 상태.

### 6.2 서비스 모델

가사지원: 한 장소에서 필수 서비스시간 동안 1명이 전담한다. 방문 전후 이동을 인력 일정에 포함한다.

병원동행: 인력이 대상자를 만나는 시점부터 병원 이동, 진료·대기·수납, 귀가 완료까지 연속 점유한다. 그 사이 다른 요청을 삽입하지 않는다. 외래 예약시각과 도착 여유를 하드 제약으로 적용한다. 병원 체류시간은 담당자가 확인한 추정치와 여유시간으로 표현하며 실제 진료시간을 보장하지 않는다.

기술 모델: OR-Tools Routing(시간창이 있는 차량경로 모델)을 1차 엔진으로 쓴다. 인력은 차량, 요청은 방문 노드로 둔다. 병원동행은 '픽업 → 병원 → 귀가'를 서비스시간이 긴 단일 노드로 모델링해, 그 사이에 다른 요청이 들어가지 않는 연속 점유를 구조적으로 보장한다. 외래 예약 도착은 노드의 시간창으로 표현한다. 휴게는 인력별 break interval로 둔다. 미배정은 우선순위별 페널티가 있는 선택적 방문으로 처리한다.

시간 단위는 정수 분이다. 계산은 서비스일 자정(Asia/Seoul) 기준 분으로 하고, 저장·API 경계에서 시각으로 변환한다. 6.4의 목적함수 순서는 페널티 크기 차이(높은 우선순위 미배정 ≫ 일반 미배정 ≫ 이동 1분)로 근사하며, 근사이므로 결과를 우선순위별 미충족률로 함께 보고한다.

모든 엔진 결과(기준선 포함)는 6.3 하드 제약을 엔진과 독립된 검증기로 다시 확인한다. 검증 실패 결과는 화면에 배정안으로 표시하지 않는다. CP-SAT(선택적 구간·NoOverlap)은 M2 이후 성능·정확도 비교 후보로 둔다.

### 6.3 하드 제약

1. 요청은 기본적으로 하나의 인력에 최대 한 번 배정.
2. 같은 인력의 근무·휴게·이동·서비스 시간은 겹치지 않음. 동행 내부 이동은 점유 구간에 포함하므로 별도로 중복 점유하지 않음.
3. 요청 필요 자격·기관 수행 범위·권역·협약 유효조건 충족.
4. 예약 도착, earliest_start, latest_finish, 필수 서비스시간, 첫 지원 마감 충족.
5. 근무시간 안에서 배정. 초과근무 기본 OFF. 허용 실험은 관리자 설정 상한 내에서만 가능하며 비용 적용.
6. 확정·진행중 일정은 기본 잠금. 변경 허용 범위와 대상자 확인이 없는 상태로 이동하지 않음.
7. 공개 API와 기관자료에서 확인되지 않은 필수값을 임의 보완하지 않음.
8. 예산 상한이 설정되고 단가가 완비되면 예산도 하드 제약. 비용 미확정 시 “동일 예산 검증” 결과를 내지 않음.

### 6.4 목적함수 순서

실행 가능한 해 안에서 (1) 높은 우선순위의 적기 필수 요청 수 최대화 → (2) 나머지 우선순위별 적기 요청 수 최대화 → (3) 동률에서 지원 가능한 고유 인원 증가 → (4) 총 이동·초과·일정변경 비용 최소화.

우선순위는 담당자가 설정하고 이유를 저장한다. 가까운 경증 대상자만 반복 배정하는 결과를 탐지하기 위해 우선순위별·권역별 미충족률도 보고한다. 필수 서비스시간 단축은 목적함수에 포함하지 않는다. 담당자 설정 우선순위는 의료 판단을 대체하지 않는다.

### 6.5 미배정 사유

| 코드 | 의미 | 표시 원칙 |
|---|---|---|
| MISSING_REQUIRED | 필수 데이터 부족 | 인력 부족 집계에서 분리 |
| ROUTE_UNKNOWN | 해당 이동수단 경로 없음·실패 | 0분으로 대체하지 않음 |
| NO_SKILL_MATCH | 유효 자격 인력 없음 | 후보 필터 결과로 확인 |
| OUT_OF_SCOPE | 기관·권역·협약 밖 | 해당 규칙 제시 |
| TIME_WINDOW_CONFLICT | 시간창 충돌 | 후보별 확인된 충돌 제시 |
| NO_CAPACITY | 유효 후보의 가용시간 부족 | 검증 가능한 범위 표시 |
| BUDGET_LIMIT | 예산 조건 초과 | 적용 단가·상한 표시 |
| SOLVER_UNRESOLVED | 계산 한도 내 미배정 원인 확정 못함 | “해결 불가능”이라고 단정 금지 |

솔버는 단일 원인을 항상 증명하지 못한다. 명확한 필터 탈락 사유와 반사실적 재계산으로 추정한 사유를 구분해 `reason_certainty = verified / diagnostic / unknown`으로 저장한다.

## 7. 상태 전이와 동시성

### 요청

`draft → needs_review → ready → cancelled/closed`

배정 상태는 요청 준비 상태와 분리한다. 요청을 ready로 바꾼 뒤 내용 수정이 배정 조건에 영향을 주면 version 증가·관련 제안 무효화. 완료된 과거 요청 수정은 원본 덮어쓰기 대신 정정 이력 생성.

### 배정

`proposed → approved_pending_acceptance → confirmed → en_route → in_progress → completed`

분기: proposed→rejected, 승인/확정→cancelled, 제안→superseded, 인력 거절→declined. 협약기관 배정은 partner_acceptance=accepted가 추가로 필요. 지연은 별도 이벤트이며 완료 상태로 전환되지 않는다. 진행중 중단은 담당자 처리 후 `interrupted`로 기록, 자동 슬롯 해제 금지.

### 승인 트랜잭션

> v1.2: M2는 단일 기관·단일 담당자 기준이다. 버전 확인, 멱등 키, 인력 점유 중복 검사는 구현하고 다기관·RLS는 후속으로 둔다.

1. JWT와 기관·역할 권한 검사.
2. idempotency_key 중복 확인.
3. 해당 기관 schedule_version과 관련 인력·요청 version 확인·잠금.
4. 최신 자료로 시간·자격·휴게·중복 재검증.
5. 승인 대기 점유와 assignment, 감사이력 저장; schedule_version 증가.
6. 승인 대기 슬롯도 다른 승인에 사용하지 못하도록 유지. 거절·담당자 만료 처리 시 명시적으로 해제.

DB 수준: `worker_occupancies`의 worker_id와 `[start_at,end_at)` 범위에 활성 점유 exclusion constraint 검토. 동일 요청의 활성 1:1 배정은 부분 unique 제약 적용. 승인 API는 서버 트랜잭션/RPC로만 실행.

## 10. AI 처리 요구사항

1. CSV/XLSX의 정형 필드는 파서로 읽는다. LLM을 모든 셀의 필수 경로로 사용하지 않는다.
2. 텍스트·모의 음성에는 STT→구조화→JSON Schema 검사→필드 근거 검사→담당자 확인 적용.
3. 결과 구조는 `field, value, evidence_source_id, evidence_span, needs_confirmation`을 포함한다. 근거가 없으면 null로 남긴다.
4. AI는 자격·의학적 필요·독거 여부·자립보행을 원문 밖에서 확정하지 않는다.
5. 원문에 포함된 지시문은 자료로 취급하며 시스템 규칙·도구 호출을 바꾸지 못한다. 추출 모델에는 일정 승인 도구를 제공하지 않는다.
6. 배정 설명은 엔진 지표와 조건 검증 결과를 기반으로 한다. 수치는 결정적 템플릿으로 렌더링하고 LLM이 수정하지 못하게 한다.
7. 공급자 장애 시 파서 입력과 담당자 확인은 계속 가능. 모의 응답을 실제 추론 성공으로 표시하지 않는다.
8. 모델명·프롬프트 버전·처리시간·비용·오류·원문 해시를 추적한다. 보관기간·외부 전송 조건은 기관 실증 전 확정한다.
9. STT/LLM 공급자는 기존 서로ON 경험과 주최 지원환경을 우선 검토한다. API 키·모델 접근 확인 전 공급자와 성능을 확정하지 않는다.
10. LLM은 11월 동안 모두의 AI 실험실 게이트웨이(`https://gateway.aitestbed.kr`, Anthropic Messages 형식 `/v1/messages` 호출 확인)를 기본 공급자로 쓴다. 팀 포인트는 12월 초 소멸하므로 공급자·주소·키·모델은 설정값으로만 두어 교체 가능하게 한다.
11. 시연용 사례의 추출 결과는 M2에서 원문 해시와 함께 저장해, 키 없이도 같은 결과로 시연할 수 있게 한다. 저장 결과를 실시간 추론 결과로 표시하지 않는다.

### 11.3 어댑터와 데이터 계약

`GeocodeProvider.search(address)`, `HospitalProvider.search(query)`, `RouteProvider.estimate(origin,destination,mode,departure_at)`, `CareInstitutionProvider.detail(code,type)`, `WeatherProvider.forecast(location,valid_at)`.

경로 저장 필드는 8장의 `duration_seconds`로 통일한다. 선정표의 duration_sec는 같은 의미이며 구현에서는 사용하지 않는다.

- 필수 공통 메타데이터: provider, fetched_at, source_version(없으면 null), data_mode(live/mock/estimated), status.
- 경로: from_id, to_id, mode, duration_seconds, distance_m, requested_departure_at, time_basis(current/forecast/provider_unspecified/synthetic), applicable_at, expires_at, provider_result_code.
- status: ok/no_route/missing_key/auth_failed/access_denied/rate_limited/timeout/provider_error/invalid_response.
- 성공일 때만 양수 duration_seconds를 반환한다. 같은 장소 무이동은 별도 검증 규칙으로 0을 허용하며 API 실패와 구분한다.
- 실패 시 시간·거리는 null. 실 API 실패를 mock 성공으로 자동 대체하지 않는다.
- 왕복은 방향별로 조회한다. 캐시 키에 공급자·수단·방향·시간 기준을 포함하며 보관 조건 확인 전 장기 캐시를 켜지 않는다.
- 현재 기준 API만 지원하면 요청한 미래 시각과 응답의 실제 시간 기준을 함께 표시한다. 미래 일정의 확정 경로로 승인하려면 승인 전 확인·재조회 정책이 필요하다.
- 지오코딩 성공은 주소 일치·출입구 접근성 확인과 다르다. 후보 선택·좌표 검토 상태를 별도 저장한다.
- 병원 체류·대기·탑승 지원·귀가 준비는 이동시간 밖의 필수 점유시간으로 더한다.

### 11.4 MCP 적용

플랫폼에서 확인한 접속 설정은 URL `https://mcp.koreaconnect.kr/sse`, type `sse`, 인증 헤더 `api_user_key_id`다. 실제 도구명·스키마·호출 권한은 로그인·인증 후 확인한다.

배정 엔진의 반복 경로 조회는 REST 어댑터로 수행한다. MCP는 담당자의 자연어 조회와 설명 보조에 사용한다. MVP에 MCP 기능을 표시하려면 인증→도구 목록 확인→승인된 읽기 도구 시험을 통과해야 한다. 통과 전 상태는 configured 또는 미연결이다. MCP를 이용해 배정 승인·실제 파견을 실행하지 않는다.

1. 1주차에 플랫폼 A03을 우선 신청하고 비용·쿼터·승인 범위를 기록한다. A05·A07은 후속 화면 일정에 따라 신청한다.

## 12. 시뮬레이션 설계

### 데이터와 평가 분리

개발용 사례와 평가용 사례의 ID·seed를 분리한다. 실제 병원 좌표를 사용할 수 있지만 대상자 위치·건강조건·요청 이력은 합성이다. 고령인구로 만든 요청량은 “가정한 수요”다.

기본 규모: 인력 20명, 평일 1개월. 요청량은 건수가 아니라 부하율로 정의한다.

- 부하율 ρ = (요청의 필수 점유시간 합 + 예상 이동시간 합) ÷ (인력 가용 근무시간 합)
- 기본 실험: ρ = 0.6(여유), 0.9(포화 직전), 1.1(초과)
- 부하가 낮으면 어떤 방식으로도 대부분 배정되므로 비교 차이가 작게 나오는 것이 정상이다. 그 결과도 그대로 보고한다.
- 작은 검증세트(2명·5건)는 수작업 정답과 비교한다.

시드는 최소 10개(42~51)를 기본 묶음으로 사용. 취소율 0/10/20%, 부하율 0.6/0.9/1.1, 이동·병원 체류시간 0.8/1/1.3배를 실험 가정으로 제공한다. 모든 조합을 무조건 실행하지 않고 기준조건에서 한 요인씩 변경한 후 중요 상호작용을 추가한다.

### 비교 알고리즘

- 신청순: 접수시각 순서로 동일 조건의 feasible 인력 중 가장 빠른 가능 시간에 배정; 동률 인력 ID 순.
- 근거리: 담당자 우선순위·마감 순으로 요청을 선택하고 feasible 인력 중 추가 이동이 가장 적은 후보 배정.
- 최적화: 6장의 목적함수와 제약 적용.
- 현장 배정안: 실제 운영기관 자료가 제공되는 후속 단계에서 추가. 가상 선착순을 실제 기관 방식이라고 명명하지 않는다.

취소·지연은 이벤트 접수 시점에 공개한다. 미래 이벤트나 실제 종료시간을 사전에 아는 알고리즘과 비교하지 않는다. 예측·계획 시간과 실행 시나리오의 실현시간을 분리한다. 월별 실험은 일별 동일 사건을 순차 재생하고 결과를 집계한다.

### 공동 동행 실험

기본 OFF. 대상자의 확인된 동의·이동조건·동시 도움 필요 여부, 병원·예약 충돌, 최대 기다림, 인력의 지원 가능 범위, 운영·보험·정산 조건을 설정값으로 관리한다. 조건이 미확정이면 실험에서 제외한다. 이동 공유와 병원 내 동시 지원을 별개의 옵션으로 둔다.

공동 인력시간은 한 번만 비용 계상하고 대상자별 혜택·대기시간을 별도로 계산한다. 조건부 실험 결과를 1:1 기본모드 성과에 합산하지 않는다. 실제 다인 동행 허용을 이 문서가 확정하지 않는다.

## 13. 비용과 자원 부족 계산

총비용 C = 인건비 + 교통비 + 기관 운영비 + 시스템비. 각 구성요소는 출처·단위·기준기간·가정 여부를 기록한다.

- 시간급: 계약상 유급시간 범위(서비스·이동·대기·보장시간)를 설정하고 계산. 서비스시간만으로 인건비 계산 금지.
- 고정급: 동일 인력을 유지하면 고정 인건비는 동일. 확보된 시간을 추가 수행 여력으로 보고하고 현금 절감으로 보이지 않게 한다.
- 교통비: 이동수단별·인원별·구간별 설정. 택시 공동 탑승 비용과 인력비를 중복 또는 누락하지 않는다.
- 비용이 미확정이면 시간·배정량만 보고한다. 분모 0이면 단가·비율은 N/A.
- 1인당 비용 = 총비용 / 적기 지원 가능 고유 인원. 함께 전체 필수요청 충족 인원 기준 단가도 표시해 부분 지원 확대를 숨기지 않는다.
- 비용 절감률 = (기준비용−대안비용)/기준비용. 지원 확대율 = 대안 적기 고유 인원/기준 적기 고유 인원. 두 지표를 임의로 동일시하지 않는다.
- 추가 자원 효과: 기본 실행과 같은 요청 집합에서 자원만 바꿔 재계산. 추가 비용/추가 적기 지원 인원을 표시하며 고우선순위·권역별 변화도 보고.

자료 미비 요청, 실제 자원 부족 진단, 계산시간 한도로 해결 못한 요청을 분리한다. 보고서에 “가상 입력 기반 추정”을 표시한다.

## 14. 기술 구조와 저장소 제안

화면(MVP): Streamlit 담당자 화면(W05·W06·W07·W09·W10·W11). 1인 개발과 5주 일정을 고려한 선택이며 React 전환은 후속이다.
엔진·서비스: Python 패키지(planner, verifier, simulator, adapters). 저장은 로컬 SQLite 기본, 공유 배포가 필요하면 Supabase Postgres.
배포: 무료 호스팅(예: Streamlit Community Cloud)으로 심사용 링크 제공. 합성 데이터만 올린다.

```text
f0/            가상 권역 생성(기존 구현, 데이터 계약에 맞춰 정리)
planner/       요청·인력 모델, 기준선(신청순·근거리), Routing 최적화
verifier/      엔진과 독립된 하드 제약 검증기
simulator/     다일·다중 시드·부하율 실험, 지표 계산
adapters/      플랫폼 API(병원·인구·기상청·ODsay), 카카오, OSRM, LLM, mock
app/           Streamlit 화면
config/        권역·실험 가정·API 설정(키 제외)
osrm/          OSRM 준비 스크립트
fixtures/      작은 검증세트·시연 사례
tests/         제약·지표·어댑터 테스트
```

MVP 첫 실행은 mock adapter로 독립 동작하되 실제 알고리즘은 계산한다. 화면에 고정 성과를 심어 시뮬레이션처럼 보이게 하지 않는다. 배포처·공급자·패키지 버전은 첫 환경 점검에서 확정한다.

하루 계산은 30초 제한으로 동기 실행하고 결과를 run_id로 저장해 새로고침 후 복원한다. 30일 시뮬레이션은 배치 스크립트로 실행하고 화면은 저장된 결과를 읽는다.

## 15. 비기능 요구사항

아래 숫자는 개발 검수 목표이며 현재 측정된 성능이 아니다.

- 응답: 기본 목록 500행 조건에서 목표 2초 이내. 실제 환경·측정값 기록.

- 안정성: API 실패·타임아웃은 명시적 실패 상태. 유효한 이전 계획 유지. 중복 승인·상태 이벤트 방지.
- 설명 가능성: 원문 필드·제약 검증·계산값·데이터 버전으로 설명을 역추적 가능.
- 운영 측정: API 사용량·비용·solver 시간·import 오류율·승인 충돌을 기록하되 개인 원문은 기록하지 않음.

| AT-19 | 원문에 “규칙 무시·승인” 지시 삽입 | 데이터로만 처리, 권한·배정 변경 없음 |
| AT-20 | 동일 입력·버전·시드 실행 | 저장된 스냅샷 재현. 다중스레드 비결정성은 설정·차이 기록 |

### 외부 연동 추가 검수

| ID | 조건·행동 | 기대 결과 |
|---|---|---|
| AT-21 | ODsay 12분·카카오 720초 | 내부 duration_seconds 모두 720, 수단 구분 |
| AT-22 | API 키 없음 또는 설정만 완료 | missing_key 또는 configured, verified 금지 |
| AT-23 | HTTP 200이지만 공급자 오류 본문 | 실패 상태, 경로값 생성 금지 |
| AT-24 | HTTP 401/403/429·시간초과 | 인증·권한·한도·시간초과 구분, 0분 대체 금지 |
| AT-25 | 음수·NaN·비정상 경로 응답 | invalid_response, 배정 입력 제외 |
| AT-26 | 미래 일정에 현재 기준 경로 | time_basis 명시, 미래 예측으로 표시 금지 |
| AT-27 | 기관코드 없는 요양기관 상세 | 코드 확보 필요, 가상 코드 생성 금지 |
| AT-28 | MCP 설정만 입력 | 도구 검증 전 사용 가능 표시 금지 |
| AT-29 | 성공·실패 점검 로그 | 키·원문·개인주소 미포함 |
| AT-30 | 공급자 HTTP 리다이렉트 | 인증 헤더를 다른 목적지로 전달하지 않음 |

핵심 제약·승인·권한 검수는 자동화한다. 화면 문구나 스타일만 복제하는 테스트는 만들지 않는다. 성능 비교는 알고리즘보다 독립적인 검증기로 제약 위반을 확인한다.

## 18. 역할과 확인 과제

당선 신청서의 역할을 개발 분담의 기준으로 사용한다. 새로운 전공·개발경력·기관 협약을 추가로 가정하지 않는다.

| 담당 | 기본 역할 | 이번 단계 산출물 |
|---|---|---|
| 김성현 | 기획 총괄·문제 정의·기관 협의 | 운영규칙·데이터 표본·서비스 범위·수용기준 |
| 정민지 | AI 파이프라인·데이터 구성 | 입력계약·원문근거·AI/공공 API 어댑터 |
| 도솔라 | 시뮬레이션·효과 검증·사용성 평가 | 기준선·가상 데이터·비용/효과 검수·시연 |
| 공동·멘토 보완 | 배정 모델·보안·배포 | 솔버 검토·권한 검수·기술 선택 |

v1.2: 개발 구현은 1인이 전담하고, 나머지 두 사람은 기관 인터뷰·운영 규칙·실험 가정·평가 자료를 맡는다.

### 착수 가능 항목과 미확정 항목

- 즉시 착수: mock 기반 화면, 합성 CSV, 1:1 엔진, 승인 상태, 평가 프레임.
- 외부 API 전: 확인한 플랫폼 자원별 사용승인·키·요금·쿼터·캐시 조건 확인. 병원 기본목록 플랫폼 상세와 기관 목록 API는 추가 확보. 카카오 직접 연결 지원 범위 확인.
- 기관 실증 전: 운영기관·지역, 자료 사용 동의·처리계약, 필수 지원·근무규칙·비용, 배정·수락·정산 권한 확인.
- 공동 동행 현장 전: 대상조건·지원 동시성·인계·책임·보험·기관 허용 범위 확인.

## 19. 와이어프레임 대비 정교화 내역

1. W05 예시에는 가사지원 R-014가 동행 전용 W-01에 놓인 표기가 있었으나 W06은 W-02를 제시한다. 구현에서는 W04의 서비스 자격에 따라 W-02 등 가사 가능 인력만 후보로 삼는다. 와이어프레임의 예시 배치는 유효 배정 결과가 아니다.
2. “근무시간 위반 금지”와 “초과근무 지표”를 일관되게 하기 위해 초과근무 기본 OFF, 허용 실험만 별도 설정으로 명시했다.
3. 승인·기관 인수·인력 수락·확정·실제 완료를 분리했다. 승인됐다는 이유로 실제 돌봄 완료로 집계하지 않는다.
4. 주 지표의 고유 인원 외에 필수 요청 전체 충족 인원을 추가했다.
5. 타임아웃 때문에 못 찾은 배정을 실제 자원 부족으로 단정하지 않도록 진단 수준을 추가했다.
6. 담당자 수정·승인과 외부 API 미연결 상태를 명시해 “입력 없이 승인만”을 절대적 약속으로 구현하지 않는다.

## 20. 최종 완료 정의

MVP 완료는 화면 11개가 보이는 것이 아니라, 합성 요청 가져오기 → 검토 → 제약을 지킨 배정 → 담당자 승인 → 취소 후 재배정 → 인력 상태 → 동일 조건 비교와 부족 자원 보고가 저장된 데이터와 계산으로 이어지는 상태다.

최종 시연은 (A) 1:1 기본 운영, (B) 취소·지연 대응, (C) 기관/인력 추가 효과, (D) 공동 동행 별도 실험의 네 장면으로 구성한다. 실제 계산된 지표만 제시하고, 연결하지 않은 API·미검증 예측·가상 데이터의 한계를 같은 화면에서 확인할 수 있어야 한다.

## 21. v1.1 개정 및 현재 구현 상태

외부 연동을 6주차에서 1~2주차로 앞당겼다. FR-48~56, AT-21~30, 플랫폼 API·MCP와 차량·주소 보완 후보를 반영했다. 제품 목표·기관 권한·연속 동행·최적화 검증 원칙은 유지한다. 연결 준비 스크립트만 작성했으며 MVP 화면·배정 엔진·실제 인증 호출은 이번 개정으로 완료되지 않았다.
